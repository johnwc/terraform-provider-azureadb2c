# terraform-provider-azureadb2c

A Terraform / OpenTofu provider for **Azure AD B2C custom policies** (Identity Experience Framework). It manages custom policy XML documents and policy keys through the Microsoft Graph `trustFramework` API (beta), on the Terraform Plugin Framework.

> Not affiliated with or endorsed by Microsoft.

## What it manages

| Type | Name | What it is |
| --- | --- | --- |
| Resource | `azureadb2c_trust_framework_policy` | One custom policy (one `<TrustFrameworkPolicy>` XML document). |
| Resource | `azureadb2c_trust_framework_key_set` | One policy key container and its key (generated by B2C or uploaded from a secret). |
| Data source | `azureadb2c_trust_framework_policy` | Reads a custom policy's XML, base policy id and tenant id. |
| Data source | `azureadb2c_trust_framework_key_set` | Reads a key container's key use, key type and key id. Key material is never read. |

## Required Microsoft Graph permissions

App-only authentication needs these Microsoft Graph **application** permissions, with admin consent, on the app registration in the B2C tenant:

- `Policy.ReadWrite.TrustFramework` (custom policies)
- `TrustFrameworkKeySet.ReadWrite.All` (policy keys)

A `403` from Graph is a missing permission, not a token problem.

## Provider configuration

Authentication is the same block as the `hashicorp/azuread` and `azurerm` providers: client secret, client certificate, OIDC / workload identity (GitHub Actions, Azure DevOps), Azure CLI and managed identity, with the usual `ARM_*` / `AZURE_*` environment variables. A `client_secret` or client certificate written in the provider block is used instead of a sign-in method that is only switched on by an environment variable (such as `ARM_USE_OIDC`), unless the block itself sets `use_cli`, `use_msi` or an OIDC option. This lets the provider share a workspace with another provider that signs in to a different tenant.

```hcl
terraform {
  required_providers {
    azureadb2c = { source = "johnwc/azureadb2c" }
  }
}

provider "azureadb2c" {
  tenant_id = "contoso.onmicrosoft.com"
  client_id = "00000000-0000-0000-0000-000000000000"
  # client_secret from ARM_CLIENT_SECRET
}
```

The provider gets a Graph token when it is configured, so wrong credentials fail before any resource is touched.

## Upload order: pass the parent's id

B2C rejects a child policy whose base policy does not exist yet, and a policy whose key container does not exist yet. Build each child policy with `templatefile()` and pass the parent's `.id` into it. Terraform then sees the dependency and uploads base, then extensions, then relying party (and deletes them in reverse). Pass key set ids into the base policy the same way.

```hcl
resource "azureadb2c_trust_framework_key_set" "token_signing" {
  id       = "B2C_1A_TokenSigningKeyContainer"
  use      = "sig"
  key_type = "RSA"
}

resource "azureadb2c_trust_framework_policy" "base" {
  policy = templatefile("${path.module}/policies/base.xml.tftpl", {
    tenant                = "contoso.onmicrosoft.com"
    signing_key_container = azureadb2c_trust_framework_key_set.token_signing.id
  })
}

resource "azureadb2c_trust_framework_policy" "extensions" {
  policy = templatefile("${path.module}/policies/extensions.xml.tftpl", {
    tenant         = "contoso.onmicrosoft.com"
    base_policy_id = azureadb2c_trust_framework_policy.base.id
  })
}
```

Right after a base policy or key container is created, B2C can still report it as missing for a short time. The provider retries the upload for up to about 2 minutes in that case only; any other upload error fails at once.

Notes on the policy resource:

- `id` is read from the `PolicyId` attribute of the root element. Changing it replaces the policy.
- Differences only in the XML declaration, comments, whitespace between elements and attribute order are not changes, so the formatting in your files is kept and the server's formatting does not cause a diff.
- Plan-time checks: well-formed XML, a `TrustFrameworkPolicy` root element, a `PolicyId` starting with `B2C_1A_`, and no unresolved `{Settings:...}` placeholder. Claim resolvers such as `{Policy:TenantObjectId}` or `{OIDC:LoginHint}` are fine.
- An existing policy is not overwritten on create. Import it with `terraform import azureadb2c_trust_framework_policy.<name> <policy id>`.

## Secrets without state: `secret_wo`

To upload a secret (for example an identity provider client secret) without storing it in plan or state, use the write-only attribute `secret_wo` with `secret_wo_version` (Terraform 1.11 or later). The secret is sent once when the key set is created. To rotate it, change the secret and bump `secret_wo_version`; that replaces the key set.

```hcl
variable "facebook_app_secret" {
  type      = string
  sensitive = true
  ephemeral = true
}

resource "azureadb2c_trust_framework_key_set" "facebook" {
  id                = "B2C_1A_FacebookSecret"
  use               = "sig"
  key_type          = "oct"
  secret_wo         = var.facebook_app_secret
  secret_wo_version = 1
}
```

`secret` does the same but keeps the value in state (sensitive). Set only one of them. An uploaded secret needs `key_type = "oct"`. Leave both unset to let B2C generate the key. Key set ids must include the `B2C_1A_` prefix. Every change to a key set replaces it, and the secret is never read back, so after an import `secret` and `secret_wo` stay unset.

## Build, test and docs

```sh
go build ./...
go test ./internal/...
cd tools && go generate ./...   # formats examples/ and regenerates docs/ (needs terraform on PATH)
```

Acceptance tests create and delete real policies and keys, so run them only against a disposable dev B2C tenant. They need `TF_ACC=1`, `ARM_TENANT_ID`, `ARM_CLIENT_ID` and a credential (`ARM_CLIENT_SECRET`, a certificate, OIDC or `ARM_USE_CLI`). The policy test also needs `AZUREADB2C_ACC_TENANT_DOMAIN` (for example `contoso.onmicrosoft.com`) and is skipped without it. Test objects are named `B2C_1A_TfAcc<random>`.

```sh
TF_ACC=1 go test -run '^TestAcc' -v ./internal/provider/
```

## Releasing

Releases are built from a release branch, never from `main`, which tracks upstream.

1. Create a GitHub release with tag `vX.Y.Z` and the release branch as its target.
2. Approve the `release` environment deployment in Actions. The workflow runs the unit tests, then GoReleaser builds and GPG-signs the binaries.
3. GoReleaser leaves the release as a draft. Publish the draft on GitHub; the Terraform Registry only picks up published releases.
4. Check the new version at `https://registry.terraform.io/v1/providers/johnwc/azureadb2c/versions`.
